Digital-asset platform: cloud platform, delivery pipeline and multi-region disaster recovery

For a US client's regulated digital-asset platform, I built the AWS environments the product runs on, the pipeline that ships it, and a disaster-recovery copy in a second region that can be created, tested and removed with one click.

Role: DevOps EngineerAWS · EKS · TerraformGitHub Actions · HelmSecurity · Disaster recovery
🔒Confidential client work. Product names, domains, account details, regions and internal designs are left out on purpose. This page describes the engineering approach and what I did, not the client's systems.
The context

A platform where downtime and leaked secrets are not an option

The platform has a customer web app, a back-office app, three backend services (authentication, customer and admin), a key-signing service and distributed-ledger nodes, backed by PostgreSQL, Redis, DynamoDB and S3.

It handles digital assets, so every layer has to be private by default, every secret has to stay out of code and images, and the business has to be able to keep running if a whole AWS region goes down.

The challenges

What had to be solved

📦 One codebase, three servicesA monorepo with three service submodules had to deploy all services together, or just the one that changed.
🔑 Secrets in the wrong placesApp configuration lived in CI secrets and could end up in image layers. It had to move into a proper secret store.
🌐 Nothing public by accidentServices needed public HTTPS endpoints without exposing load balancers or the cluster to the internet.
🌍 Surviving a region outageThe business needed a hot copy in a second region with minutes of data loss at most, and a safe way to test it.
✍️ Never sign twiceIn a two-region setup, the signing service must only ever be active in one region at a time.
💰 Cost controlEnvironments and the DR copy had to be cheap to run, and possible to remove completely when not needed.

What I did

My work, layer by layer

🏗️

Infrastructure as code with Terraform

Built the development and staging environments on AWS as independent Terraform stacks, each with its own remote state and locking, applied in a defined order.

  • Network with public, private and data subnets across availability zones, NAT and VPC endpoints.
  • EKS with separate node groups for apps, the signing service and ledger nodes, kept apart with taints and affinity.
  • Databases, cache, storage, certificates, CDN, API gateway, cluster add-ons and per-service IAM roles as code.
  • Solved real rollout blockers, such as nodes starting before outbound internet existed, by fixing dependencies and quotas.

🚀

CI/CD for a monorepo with service submodules

Designed the GitHub Actions pipeline that builds one image for all backend services and deploys them with a shared Helm chart.

  • A push to the main repository deploys every service; a push to one service repository triggers a deploy of only that service.
  • Images built with BuildKit and pushed to the registry with traceable commit tags; private package tokens passed as build secrets, never stored in a layer.
  • Helm releases per service with the rollout status checked, so a failed deploy turns the pipeline red.
  • Separate pipelines for the web apps (static build to a private bucket behind the CDN), plus a low-cost single-machine dev environment.
GitHub ActionsDocker BuildKitAmazon ECRHelmCloudFront
🛡️

Security hardening

Made private-by-default the rule at every layer.

  • Containers run as a non-root user with all Linux capabilities dropped, no privilege escalation and the default seccomp profile.
  • Moved application configuration out of CI secrets into AWS Secrets Manager, synced into the cluster by External Secrets.
  • Replaced long-lived CI access keys with GitHub OIDC roles limited to one branch and environment, and gave each service its own IAM role.
  • Kept load balancers internal and published APIs only through the API gateway over a private link; web apps only through the CDN with a web firewall.
  • Enforced verified TLS from the services to the database.
IAM / OIDCSecrets ManagerExternal SecretsAWS WAFKMS
🌍

One-click multi-region disaster recovery

Turned the whole platform into a region-portable copy that runs hot in a second AWS region.

  • Removed region-specific values from all 16 infrastructure stacks so the same code deploys to any region, with its own state stored in the DR region.
  • One pipeline to create, sync and decommission the DR copy, with safe teardown that only ever touches DR resources.
  • Continuous replication: cross-region database read replicas, global tables, storage replication, mirrored container images and secrets.
  • The signing service is deployed but fenced in the DR region, so only one region can sign at a time.
  • Health checks and alarms on the primary region, and a written runbook for failover, fail-back and decommission.

Outcomes

What changed for the team

  • Every environment is reproducible from code instead of built by hand
  • Deploys run automatically per service, with rollouts verified
  • No long-lived AWS keys in CI, no secrets in images
  • Nothing internal is reachable from the internet
  • A tested, documented path to survive a full region outage
  • DR can be removed and rebuilt on demand to control cost
